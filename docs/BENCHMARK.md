# EFM vs Cardinal 벤치마크

측정일 2026-10-13. 재현: `tools/bench/run.sh [폴더]`

## 방법

- 같은 기기에서 같은 폴더(`$HOME`, 약 379만 항목, 고유 이름 148만 개)를 각자 새로 색인한 뒤, 같은 질의 15개를 5번씩 실행했다.
- Cardinal 쪽은 앱이 아니라 Cardinal의 검색 엔진 크레이트(`search-cache`, 커밋 `4c50734`)를 직접 호출하는 Rust 프로그램이다(`tools/bench/cardbench`). UI와 IPC 비용이 빠지므로 Cardinal에 유리한 비교다.
- 둘 다 Cardinal 기본값인 대소문자 무시 모드로 측정했다.
- EFM 시간은 정렬까지 포함한다(기본 이름순). Cardinal은 이름 색인 순서로 결과를 내므로 별도 정렬이 없다.
- 기기: Apple M5 (10코어), 16GB, macOS 27.0. 릴리스 빌드.

## 차이가 나는 이유 (구조)

| 부분 | Cardinal | EFM |
|---|---|---|
| 이름 저장 | 고유 이름을 `BTreeSet<Box<str>>`에 저장(이름마다 별도 할당) | 고유 이름을 연속된 바이트 덩어리 3벌(원본, NFC, 소문자)로 저장 |
| 이름 매칭 | 뮤텍스를 잡고 단일 스레드로 BTree 순회, 대소문자 무시 시 이름마다 정규식 실행 | 전체 코어 + NEON SIMD 부분 문자열 검색(접은 이름 위에서 바로 비교) |
| AND / OR / NOT | 조건마다 결과 `Vec` 생성 후 `HashSet`으로 교집합·차집합 | 항목 비트셋끼리 64비트 단위 비트 연산 |
| 크기·날짜 | 스캔 때 수집 안 함, 질의 때 `lstat` | `getattrlistbulk` 한 번으로 이름과 함께 수집 |
| 정렬 | 결과를 받을 때마다 `sort_by` | Everything 방식: 미리 정렬한 순열을 비트셋으로 거르고 변경분만 병합 |
| 한글 정규화 | 질의를 NFC/NFD로 두 번 검색 후 병합(섞인 이름은 놓침) | 색인 때 한 번 정규화, 검색은 한 번 |
| 정규식 | Rust `regex`로 모든 고유 이름 검사 | 패턴에서 필수 리터럴을 뽑아 SIMD로 먼저 거른 뒤 후보에만 정규식 |
| 스캔 | `read_dir` + rayon | `getattrlistbulk` + 작업 큐 스레드 |

## 해석할 때 주의할 점

- 두 색인은 몇 분 간격으로 만들어서 항목 수가 조금 다르다(약 2,500개, 0.07%).
- 측정은 한 기기, 한 폴더 기준이다. 루트 전체(`/`)나 다른 기기에서는 숫자가 달라질 수 있다.
- EFM의 이름순은 접은 이름(소문자 NFC) 기준이고 Cardinal은 원본 바이트 기준이라, 결과 순서가 완전히 같지는 않다.
